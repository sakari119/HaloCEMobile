# Trevor web crash on Galaxy S24

The user ran the GitHub Pages web port in Chrome 154.0.8037.92 on a Galaxy S24 with Android 16. The game image was `Halo - Combat Evolved (USA).xiso`. The user saw a page crash during campaign play. An Android Debug Bridge (ADB) log captured one repeat on 2026-10-02.

At 00:27:32, Chrome reported `GL_INVALID_OPERATION: glBlitFramebuffer: Blit feedback loop: the read and draw framebuffers are the same.` In `port/linux/src/d3d8_gl.c`, `framebuffer_get()` binds `GL_FRAMEBUFFER` on a cache miss. `D3DDevice_Present()` previously bound draw framebuffer 0 before that call. A cache miss replaced both bindings with the read framebuffer. The fix gets the read framebuffer first, then binds draw framebuffer 0.

At 00:27:53, Android's low-memory killer started to reclaim background processes. At 00:28:04, it killed a foreground Chrome sandbox process and Chrome itself. Chrome then closed. The log supports memory pressure as the direct cause of this page closure. It does not show which allocation caused the pressure. The graphics error happened about 30 seconds earlier, so its role in the memory event is unknown.

The universal APK also ran on the phone during the first capture. Android reclaimed its background process at 00:27:58. The universal APK passed the scene that crashed in Chrome, but it uses a different display path.

A second run showed `Aw, Snap!` while Chrome stayed open. Android closed the universal activity before the web run. Available memory fell from 2,829,548 KB at 00:39:35 to 658,384 KB at 00:40:11. Android killed the foreground Chrome sandbox process at 00:40:16. Available memory rose to 4,199,048 KB at 00:40:17. Chrome reported the same framebuffer error at 00:39:44. The second log supports a memory kill even when the universal activity is closed. The sample covers Chrome's main process, but it does not show the sandbox process memory by itself.

The web build starts with a 0x88000000-byte WebAssembly memory, about 2.125 GiB. This is an address-space requirement. The captured log does not show how many of those pages were resident. Do not claim that the full allocation was in physical RAM.

## Tests with a patched web build

The `D3DDevice_Present()` fix reached the phone through a temporary replacement of `halo.wasm` in Chrome's active site cache. The patched game opened its menu. The framebuffer error did not recur in that run. Android still killed the foreground Chrome sandbox process at 01:07:23 after an `Aw, Snap!` crash.

Android's `dumpsys meminfo -d` showed rapid growth in Chrome's GPU process, PID 11684. Its `EGL mtrack` rose from 18,263 KB at 01:06:49 to 3,504,999 KB at 01:07:19. Available system memory fell to 649,136 KB. The GPU allocation then fell when Android killed the page. Thus, the framebuffer error and the memory crash are separate faults.

## Bitmap isolation tests

The web worker calls `OffscreenCanvas.transferToImageBitmap()` in `port/web/src/web_library.js` for each frame. The page gives each bitmap to a `bitmaprenderer` canvas in `port/web/site/app.js`.

In one test, the page displayed one bitmap in ten and closed the other nine. The worker still created all bitmaps. GPU `EGL mtrack` rose from 364,807 KB at 01:13:08 to 3,700,535 KB at 01:14:20. Android killed the page again. This excludes the page's display call as the main cause.

In the next test, a temporary change in cached `halo.js` made the worker create one bitmap in ten. The game kept running at the menu. GPU `EGL mtrack` rose from 29,879 KB at 01:16:37 to 457,735 KB at 01:18:09. Growth was about one tenth of the normal rate. The test ties the GPU memory growth to worker bitmap creation or transfer. It does not isolate which browser operation retains the memory.

These tests did not enter the campaign. The memory failure occurs at the main menu, so the cutscene is not required to reproduce it. The one-in-ten test reduces the display rate to about 2 frames per second. It is a diagnostic test, not a usable fix. A proper fix needs a display path that avoids a new transferred bitmap for each frame, or evidence that Chrome reclaims those bitmaps under another transfer method.

The raw Android Debug Bridge (ADB) logs and memory samples are in ignored `Agent_Test_Output/`. They can include private device data. Do not commit or share the raw files. The original `halo.wasm` and `halo.js` cache entries were restored after testing. The two universal-project agents received notice that the phone is free.
